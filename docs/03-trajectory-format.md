# 03. Файл траектории: откуда взять и как разобрать

## 1. Почему STL нельзя «перевести в траекторию» напрямую

STL — это **триангулированная поверхность** (набор треугольников), а не траектория
движения инструмента. В STL нет ни понятия «фреза», ни порядка обхода, ни подачи,
ни глубины резания. Один и тот же меш можно обработать десятком разных траекторий
в зависимости от инструмента и стратегии.

Поэтому между STL и приложением обязателен шаг **CAM** (Computer-Aided Manufacturing):
он строит траекторию центра фрезы и выгружает её в **G-code** — текстовый стандарт
ISO 6983, который понимает любой станок и который мы умеем разбирать.

```
STL ──► CAM (выбор фрезы, стратегии, подачи) ──► G-code (.nc/.gcode/.tap) ──► наше приложение
```

## 2. Чем получить G-code из STL

| Инструмент | Лицензия | Комментарий |
|---|---|---|
| **FreeCAD + Path** | бесплатно | полностью бесплатный путь: импорт STL → Job → Contour/Adaptive → Post-processor «GRBL» или «LinuxCNC» |
| **Fusion 360 (CAM)** | бесплатно для личного использования | самый удобный 2.5D/3D CAM, постпроцессор «GRBL»/«Fanuc» даёт чистый G-code |
| **MeshCAM** | платно (trial) | простой 3D-CAM специально под STL |
| **Blender + CAM-плагин** | бесплатно | если уже работаете в Blender |
| **ESTLCAM / pyCAM** | платно / бесплатно | 2.5D-обработка, простые постпроцессоры |
| **PrusaSlicer / OrcaSlicer** | бесплатно | это слайсеры для 3D-печати, но выдают валидный G-code; годятся для быстрой проверки цепочки, а не для реальной фрезеровки |

Что важно при выгрузке:

* постпроцессор должен выдавать **G0/G1 с X/Y/Z** (GRBL, LinuxCNC, Fanuc — подходят);
* не нужны компенсации инструмента (G41/G42), смена инструмента (T/M6), циклы
  сверления (G81…) — наш парсер их игнорирует;
* единицы — миллиметры (`G21`), координаты — абсолютные (`G90`);
* координаты в G-code — в системе координат заготовки; для нашей задачи удобно
  считать, что это **система базы робота** (`base`), а первая точка совпадает с
  положением робота в начале EGM-сессии.

## 3. Минимальный пример: замкнутый квадрат (5 точек)

Файл `VisualStudio/FrezaEgm/data/trajectory.gcode`:

```gcode
; Замкнутый квадрат 100x100 мм на высоте Z = 600 мм, один проход.
G21 ; единицы — миллиметры
G90 ; абсолютные координаты
G1 X750 Y0 Z600 F300
G1 X850 Y0 Z600
G1 X850 Y100 Z600
G1 X750 Y100 Z600
G1 X750 Y0 Z600
```

> Высота Z = 600 мм выбрана, чтобы робот не попадал в сингулярность запястья:
> при Z = 300 и ориентации «инструмент вверх» контроллер выдавал
> `50456 - Close to singularity`. В RAPID-модуле home = (750, 0, 600) и
> ориентация `[0, 1, 0, 0]` (инструмент смотрит вниз).

Пятая точка совпадает с первой — квадрат замкнут, робот возвращается в начало.
Первая точка намеренно совпадает с `home` в RAPID-модуле: EGM получает
**абсолютные координаты TCP** в базовой системе, поэтому первая цель равна `home`.

Тот же набор точек в простом формате — `data/trajectory.xyz`:

```
750 0 300
850 0 300
850 100 300
750 100 300
```

## 4. Что поддерживает парсер

Формат определяется автоматически по первым непустым строкам (`DetectFormat`):
если строка начинается с `G`/`M`/`T`/`N`/`S` и цифры — это G-code, иначе — XYZ.

| Поддержано | Поведение |
|---|---|
| `G0`, `G1` | линейное перемещение (модальная команда: `G1` действует до следующей `G0/G1`) |
| `X… Y… Z…` | координаты; отсутствующие оси сохраняют прежнее значение |
| `G90` / `G91` | абсолютные / относительные координаты |
| `G20` / `G21` | дюймы (×25.4) / миллиметры |
| `F…`, `S…`, `T…`, `M…`, `N…` | игнорируются (геометрия от них не зависит) |
| `; комментарий` | до конца строки |
| `(комментарий)` | удаляется, вложенность поддерживается |
| пустые строки, `\r\n` | игнорируются |

| Не поддержано | Что происходит |
|---|---|
| `G2`/`G3` (дуги) | берётся только **конечная** точка, в предупреждениях счётчик дуг |
| `G81…G89` (циклы), `G41/G42`, `G43` | игнорируются как неизвестные `G` |
| `I/J/K` | игнорируются |
| `G91` + дуги | комбинация не проверяется, работает как отрезок |

Если в файле меньше двух точек — загрузка отклоняется с сообщением.

## 5. Как из траектории получается массив точек

Алгоритм (`src/trajectory.cpp`):

1. Файл читается целиком как байты, снимается BOM UTF-8.
2. Определяется формат.
3. Для G-code поддерживается **модальное состояние**:
   `absolute` (G90/G91), `scale` (G20/G21), `motion` (G0/G1), `position` (текущая точка).
4. Строка очищается от комментариев и разбивается на слова вида `X12.5`.
5. Каждое слово разбирается в пару «буква → число»; координаты применяются к
   `position` с учётом абсолютности и масштаба.
6. Если в строке была хотя бы одна координата — точка добавляется в массив.
7. Подряд идущие одинаковые точки схлопываются (эпсилон 1e-9).
8. Результат: `std::vector<Point3>` в миллиметрах.

Для формата XYZ: в каждой строке числа разделяются пробелами, запятыми или
точками с запятой; берутся первые три (если их два — `z = 0`).

## 6. Что печатается в CSV и в каком виде уходит в EGM

CSV хранит **абсолютные** координаты — так их удобно проверять глазами и
сравнивать с CAM. В EGM уходят те же абсолютные координаты TCP в базовой системе
(`corr_frame = [[0,0,0],[1,0,0,0]]`, `EGM_FRAME_BASE`).

Первая точка файла обязана совпадать со стартовой позой робота (RAPID `MoveJ home`),
иначе первый пакет «дёрнет» робота в сторону.

## 7. Ограничения и направления развития

* Нет интерполяции: между точками робот движется по своей траектории EGM
  (ограничение `MaxSpeedDeviation`), а не с заданной подачей.
* Нет управления ориентацией: фреза сохраняет ориентацию стартовой позы.
* Дуги огрубляются до отрезков — для чистовой фрезеровки из CAM лучше заранее
  выставить «линеаризацию дуг» в постпроцессоре.
* Для реальных УП стоит добавить: `G2/G3` с разбиением, `G90.1`, плоскости `G17/G18/G19`,
  коррекцию длины инструмента.
