# 05. EGM, protobuf 3 и nanopb

## 1. Что такое EGM

**EGM (Externally Guided Motion)** — опция RobotWare `689-1`, позволяющая внешнему
устройству (нашему ПК) управлять движением робота в реальном времени. Обмен идёт
по UDP пакетами protobuf:

```
    ПК (сенсор)                                   Контроллер (робот)
        │                                                  │
        │  1. EGMSetupUC / EGMActPose / EGMRunPose  ────────┤  (RAPID)
        │                                                  │
        │◄────────── EgmRobot (mtype = DATA) ──────────────┤  поток 4–8 мс
        │                                                  │
        ├──────────► EgmSensor (mtype = CORRECTION) ──────►│  наш ответ
        │                                                  │
        │◄────────── EgmRobot (DATA) ──────────────────────┤
        │              ...                                 │
```

Важно: **адрес назначения для ответа берётся из входящего пакета** (`recvfrom`).
Поэтому клиенту не нужно знать IP контроллера: он просто отвечает тому, кто
прислал пакет. Это работает и в симуляции (`127.0.0.1`), и с реальным роботом.

## 2. Режимы EGM

| Режим | RAPID | Что передаёт сенсор |
|---|---|---|
| Позиционный (pose guidance) | `EGMActPose` + `EGMRunPose` | абсолютную позу TCP в декартовых координатах — **используется в проекте** |
| По шарнирам (joint guidance) | `EGMActJoint` + `EGMRunJoint` | углы шести осей |
| Коррекция пути (path correction) | `EGMSetupUC … \PathCorr` | малое смещение относительно запрограммированного пути |

Станция `RobotStudio/FrezaEGM` работает в pose-режиме (`\Pose`), порт **6510**,
EGM-устройство `UCdevice`; адрес назначения — `SIO.cfg` → `COM_TRP` → `RemoteAdress` (в симуляции `127.0.0.1`, для реального робота — адрес ПК).

## 3. Что именно мы отправляем

Сообщение `EgmSensor` (см. `Egm/egm3.proto`):

| Поле | Значение |
|---|---|
| `header.seqno` | счётчик, +1 на каждое сообщение (по нему видно потери) |
| `header.tm` | `GetTickCount()` — метка времени, мс |
| `header.mtype` | `MSGTYPE_CORRECTION` (3) |
| `planned.cartesian.pos.x/y/z` | **абсолютная поза TCP** в базовой системе, мм |
| `planned.cartesian.orient` | единичный кватернион (ориентация не управляется) |

### Почему абсолютные координаты, а не смещения

`EGMActPose` создаёт систему коррекции; в нашем модуле это **базовая система**
(`corr_frame = [[0,0,0],[1,0,0,0]]`, `EGM_FRAME_BASE`). Поэтому сенсор обязан
присылать **позу TCP в базе**, а не приращение:

```
planned.cartesian.pos = p_i   (например 750, 0, 600)
```

Если послать смещение (0,0,0), контроллер поймёт это как «TCP в начало базы» и
робот уедет к основанию — именно так выглядел дрейф «к себе и вниз».
Первая точка файла должна совпадать с `home` робота, тогда первое сообщение
ничего не меняет.

## 4. Тайминги

| Параметр | Значение по умолчанию | Комментарий |
|---|---|---|
| период отправки | 4 мс (250 Гц) | ABB рекомендует 4–8 мс для EGM |
| темп интерполяции | шаг 2 мм, скорость 50 мм/с → 40 мс на подточку | задаётся в GUI |
| досылка на вершине | до 2000 мс, допуск 0.1 мм | чтобы не срезать угол |
| таймаут ожидания контроллера | 120 000 мс | пока RAPID не дошёл до `EGMRunPose` |
| приём | `recvfrom` с таймаутом 200 мс | не блокирует остановку |

Если сенсор перестаёт слать сообщения, контроллер завершает сессию EGM
(`ERR_UDPUC_COMM` в RAPID-обработчике `ERROR`). Поэтому после последней точки
клиент продолжает отправлять последнюю (режим `Finished`), пока пользователь не
нажмёт «Стоп».

## 5. protobuf: что это и как устроено

`.proto` — **схема** сообщений: номера полей, типы, вложенность. Из неё `protoc`
генерирует код для нужного языка. В потоке передаются только **номера полей и
значения** (тег + длина + данные), имена полей в поток не попадают, поэтому
схема на проводе совместима с любой языковой реализацией.

### proto2 → proto3: что пришлось изменить

| proto2 (`Egm/egm.proto`) | proto3 (`Egm/egm3.proto`) |
|---|---|
| `required` / `optional` | метки убраны; для части полей оставлен `optional` (explicit presence) |
| `[default = …]` | запрещено, значения по умолчанию задаёт рантайм |
| первое значение enum произвольное | первое значение обязано быть `0` (у ABB уже так) |
| поля с `required` всегда в потоке | поля со значением `0` **не передаются** |

### Ловушка с нулями — и почему `optional`

У ABB `EgmCartesian.x/y/z` объявлены `required`. Если отправить в proto3 точку
`(0, 0, 0)` без метки `optional`, все три поля будут выброшены как «значения по
умолчанию», и proto2-парсер контроллера получит сообщение без обязательных полей.

Решение: в `egm3.proto` эти поля объявлены `optional`, а клиент выставляет
`has_x/has_y/has_z = true`. Тогда нули уходят в поток явно. Это проверяется
самотестом («y = 0 передаётся явно»).

### Реальные байты

Сообщение с позой TCP `(10, 0, 0)`, `seqno = 42`, `tm = 1000` — 80 байт
(в сообщение входит ориентация — единичный кватернион):

```
0A 07 08 2A 10 E8 07 18 03   12 45 12 43 0A 1B 09 00 00 00 00 00 00 24 40
11 00 00 00 00 00 00 00 00   19 00 00 00 00 00 00 00 00 12 24 09 00 00 00
00 00 00 F0 3F 11 00 00 00   00 00 00 00 00 19 00 00 00 00 00 00 00 00 21
00 00 00 00 00 00 00 00
```

Разбор:

| Байты | Смысл |
|---|---|
| `0A 07` | поле 1 (`header`), длина 7 |
| `08 2A` | поле 1 (`seqno`) = 42 |
| `10 E8 07` | поле 2 (`tm`) = 1000 |
| `18 03` | поле 3 (`mtype`) = 3 (`MSGTYPE_CORRECTION`) |
| `12 45` | поле 2 (`planned`), длина 69 |
| `12 43` | поле 2 (`cartesian`), длина 67 |
| `0A 1B` | поле 1 (`pos`), длина 27 |
| `09 …24 40` | поле 1 (`x`) типа `double` = 10.0 (IEEE-754, little-endian) |
| `11 00…` | поле 2 (`y`) = 0.0 — **присутствует явно** |
| `19 00…` | поле 3 (`z`) = 0.0 — присутствует явно |
| `12 24` | поле 2 (`orient`), длина 36 — единичный кватернион `u0=1, u1=u2=u3=0` |

Эти же байты видно в Wireshark (фильтр `udp.port == 6510`), если нужно проверить
обмен без отладчика.

## 6. nanopb: подходит ли «урезанная» версия

**nanopb — это не protobuf-lite и не «обрезанный protobuf»**, а отдельная
C-реализация protobuf с фиксированной памятью. На проводе она полностью
совместима: тот же тег/длина/значение.

| Возможность | nanopb | Полный protobuf C++ |
|---|---|---|
| Кодирование/декодирование | да | да |
| Динамические сообщения, reflection, JSON, текст | нет | да |
| Память | статические структуры, без `new` | куча, арены |
| `repeated` | массив фиксированной длины (`max_count`) | `RepeatedField` |
| `string` | `char[max_size]` | `std::string` |
| Размер кода | десятки КБ | мегабайты + DLL |
| Сборка в MSVC | обычные `.c`-файлы | нужен собранный под MSVC runtime |

Для EGM этого достаточно: сообщения состоят только из чисел, enum и вложенных
сообщений; reflection и JSON не нужны. Ограничения (нужно задавать `max_count`,
нет `map`) для EGM не мешают — осей ровно 6.

### Генерация кода

```powershell
# из каталога VisualStudio/FrezaEgm
powershell -NoProfile -ExecutionPolicy Bypass -File .\tools\generate_proto.ps1
```

Скрипт вызывает:

```powershell
protoc --plugin=protoc-gen-nanopb=<nanopb>\generator\protoc-gen-nanopb.bat `
       --nanopb_out=<проект>\generated -I. egm3.proto
```
из каталога `Egm/` (чтобы нашёлся `egm3.options`) и кладёт результат в
`generated/egm3.pb.c` и `generated/egm3.pb.h`.

Требования к `protoc`: **≥ 3.15** (нужен proto3 `optional`). Проверено на 33.6.
`protoc` 3.7.1 (когда-то лежал в `Egm/lib/protobuf_installed`, в этой копии отсутствует) не годится: он ещё не
знает `optional` в proto3 и, кроме того, не запускается без MinGW-DLL.

`egm3.options` задаёт:

```
* mangle_names:M_STRIP_PACKAGE     # abb_egm_EgmSensor -> EgmSensor
EgmJoints.joints          max_count:6
EgmExternalJoints.joints  max_count:6
EgmCartesianSpeed.value   max_count:6
EgmTestSignals.signals    max_count:6
EgmMeasuredForce.force    max_count:6
```

Без `max_count` nanopb делает `pb_callback_t` (ручные колбэки) — это рабочий, но
неудобный вариант; с `max_count` получаются обычные массивы `double joints[6]`.

### Почему не полный protobuf C++

В старой копии в `Egm/lib/protobuf_installed/lib` лежали `libprotobuf.a`, `libprotobuf-lite.a`,
`libprotoc.a` — это сборки **MinGW**, их нельзя линковать в MSVC (другой ABI,
другой формат библиотек). Пришлось бы собирать protobuf из исходников под MSVC
(долго, десятки файлов, плюс зависимости) ради функциональности, которая в EGM не
используется. nanopb решает задачу теми же исходниками, что и приложение.

## 7. Где это в коде

| Что | Файл |
|---|---|
| Схема | `Egm/egm3.proto`, `Egm/egm3.options` |
| Сгенерированные типы | `generated/egm3.pb.h` (`EgmSensor`, `EgmRobot`, `EgmCartesian`, …) |
| Сборка сообщения | `EncodeEgmSensor()` в `src/egm_client.cpp` |
| Разбор ответа | `EgmClient::Impl::ApplyRobot()` |
| Цикл обмена | `EgmClient::Impl::Worker()` |
