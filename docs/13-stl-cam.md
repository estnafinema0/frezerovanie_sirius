На исходном HEAD STL/OpenCAMLib не реализованы. Фактически:

- `LoadTrajectory`: G-code и XYZ; G0/G1, G90/G91, G20/G21, комментарии. Дуги

- XYZ: пробелы/запятые, два числа означают Z=0. `;` сначала обрабатывается как
  начало комментария, поэтому обещание старой документации о `x;y;z` неточно.
- `ReadPointsCsv`: CSV, заголовок/мусор пропускаются, запятая/`;`/табуляция,
  три координаты либо индекс и координаты. Запись: прежний `index,x,y,z`, CRLF,
  шесть десятичных знаков. Поведение всех этих функций сохранено.
- `OnStartTrajectory` использует **абсолютные** `state.points`. `ToDeltas` не вызывается.
- `InterpolatePath` даёт первую выдержку 200 мс; концы исходных отрезков — вершины.
  Сервер сохраняет минимум 20 мс на цель и существующую досылку вершин.
- `EncodeEgmSensor` явно передаёт нули XYZ и все четыре компоненты единичного
  кватерниона. RAPID управляет только XYZ; сериализация ориентации не изменена.
- `points_selftest.csv` исторически содержит Z=300; остальные три исходных файла
  содержат Z=600. Этот старый файл тоже сохранён и проверяется отдельно.

## Поддерживаемая геометрия

Первая стратегия намеренно узкая: **замкнутый прямоугольный параллелепипед,
параллельный осям детали, 8 углов, 12 треугольников, по 2 на грань**.
Проверяются уникальность треугольников, принадлежность углам, диагонали граней,
полное покрытие всех шести граней и двукратная встречаемость каждого ребра.
Таким образом, bounding box не выдаётся за контур произвольной модели.
Даже корректный более подробно триангулированный блок пока отклоняется.
Наклоны, отверстия, выпуклые/вогнутые поверхности и произвольные меши не поддержаны.

На каждой из четырёх сторон выполняется настоящий `ocl::PathDropCutter`
с `ocl::CylCutter(diameter, length)`, всей поверхностью STL и нижним уровнем ниже
детали. Проверяются наличие контакта, конечность CL/CC, высота контакта,
принадлежность всей последовательности прямой и совпадение концов стороны.
Только затем точки сокращаются до концов. Путь имеет 5 точек, включая замыкание.

**Центр торца фрезы идёт по границе верхней грани**: радиального смещения на
половину диаметра нет. Диаметр участвует в расчёте контакта OCL. Торец касается
поверхности; эта демонстрация не задаёт снятие материала, змейку или несколько слоёв.
Длина геометрического CylCutter по умолчанию 20 мм; она не прибавляется к TCP.

После переноса и после существующей интерполяции проверяется каждый **целый
отрезок**, а не только вершины: концы должны принадлежать одной стороне в порядке
обхода, двигаться вперёд и сохранять плоскость Z верхней грани. Проверяются замыкание
и ровно один периметр. Для доказанного плоского блока это аналитическая проверка
всех точек отрезка: цилиндр над торцом не проникает в меш (в пределах допуска).
Хорда, срезающая угол, отклоняется даже при концах на границе.
Это проверка геометрии детали, **не** проверка столкновений робота/держателя,
досягаемости или фактической траектории контроллера.

Ограничения: файл 16 MiB, 100000 треугольников при чтении, 200000 CAM/интерполированных
точек, координаты STL после масштаба ±1e6 мм. Параметры конечны и ограничены.
ASCII STL разбирается по грамматике; binary — по точному размеру `84+50*N`, включая
заголовки, начинающиеся с `solid`. NaN/Inf, пустые/усечённые/вырожденные модели
отклоняются. Нормали проверяются на конечность, геометрия определяется вершинами.

## Подключение и интерфейс

`include/cam.h`, `src/cam.cpp` не зависят от EGM. Путь подключения:

```
STL → LoadStl → доказательство применимости → CylCutter/PathDropCutter
    → проверка/сокращение → явный перенос в базу → проверка → state.points
    → OnStartTrajectory → прежний InterpolatePath → проверка всех отрезков
    → прежний StartStream → EgmClient::Start → EncodeEgmSensor → UDP
```

В правом нижнем блоке окна:

1. Явно выбрать мм или дюймы (изначально выбор пустой), масштаб, диаметр, шаг CAM.
2. Ввести XYZ переноса в **мм базы**. `p_base = p_stl * units_factor * scale + t`.
   Поддерживается только перенос, матрица поворота единичная. Наклон и управление
   ориентацией добавить через этот интерфейс невозможно.
3. «STL → рассчитать…» или перетащить один STL. Unicode и пробелы передаются через
   Win32 W API и `std::filesystem::path`.
4. Проверить единицы, масштаб, размеры, преобразование и итоговые границы в диалоге.
   OK заменяет точки целиком, Cancel сохраняет прежние. Ошибка не изменяет источник.
5. «Сохранить CSV…» экспортирует результат прежней функцией.
6. «Запустить траекторию» — отдельное действие. При CAM проверяется совпадение
   первой точки с действующим home `[750,0,600]`: подвод от home не генерируется.

Кнопка «Демо 20×20» явно выбирает мм, масштаб 1 и перенос `[750,0,599.5]`.
Это **пример, не измеренная калибровка стенда**. Диаметр 4 и шаг CAM 0.5 заданы
в полях при старте окна. Изменение полей после расчёта не меняет загруженный
результат — для применения параметров нужен новый расчёт.

Расчёт синхронный в UI до открытия EGM, с ограничениями ресурсов; во время него
окно может кратковременно не отвечать. В рабочем потоке EGM нет STL, CAM или проверок.
Во время активного обмена импорт STL/G-code/XYZ/CSV не заменяет источник.
Все старые кнопки загрузки, сохранения, запуска, Stop, Home и ручных команд сохранены.
Импорт CSV не восстанавливает CAM-метаданные и работает как прежняя загрузка координат.

## Воспроизводимая Windows x64 / MSVC 2022 сборка

Используется исходный [OpenCAMLib, commit 1a450b7c3d3b669224a2a5d09aab7f319794574c](https://github.com/aewallin/opencamlib/tree/1a450b7c3d3b669224a2a5d09aab7f319794574c),
C++ DLL, без Python/Node/OpenMP. Boost 1.87.0 — только заголовки, архив SHA256
`f55c340aa49763b1925ccf02b2e83f35fdcf634c9d5164a2acb87540173c741d`.
Зависимость собирается тем же MSVC, x64, с /MD (Debug: /MDd).
Никаких MinGW-библиотек, локальных Mac-путей или изменений Protobuf.
OpenCAMLib распространяется под LGPL-2.1-or-later: при распространении DLL
сохраняйте лицензию и доступ к соответствующему исходному коду зависимости.

Требуются Git, CMake 3.20+ (рекомендуется 3.31), VS2022 с Desktop development with
C++, Windows SDK, PowerShell, `tar`. Из корня репозитория в PowerShell:

```powershell
cd VisualStudio/FrezaEgm
./tools/build_opencamlib.ps1 -Configuration Release
$deps = Join-Path $pwd 'out/deps'
cmake -S . -B build-cam -G "Visual Studio 17 2022" -A x64 `
  -DFREZA_ENABLE_CAM=ON "-DCMAKE_PREFIX_PATH=$deps/ocl-Release" `
  "-DBOOST_ROOT=$deps/boost_1_87_0"
cmake --build build-cam --config Release --parallel 4
ctest --test-dir build-cam -C Release --output-on-failure
./build-cam/Release/FrezaEgm.exe
```

Скрипт проверяет commit и чистоту checkout зависимости, SHA256 архива Boost.
Чужие изменения не сбрасывает: при несовпадении нужен новый `-Root`.
`libocl.dll` копируется CMake рядом с использующими CAM exe.
Для Debug соберите зависимость с `-Configuration Debug` и укажите `ocl-Debug`;
не смешивайте Debug/Release DLL. Пресет `x64-cam-release` доступен в VS2022
после установки зависимости в стандартный `out/deps`.

Офлайн-расчёт и экспорт без GUI и без открытия UDP:

```powershell
./build-cam/tests/Release/FrezaEgm_cam_cli.exe `
  data/cam/Primer1.STL data/cam/Primer1-base.csv mm 1 4 0.5 750 0 599.5
# Аргументы: input output units scale diameter_mm sampling_mm tx ty tz
```

Прежний режим, полностью без OpenCAMLib и Boost:

```powershell
cmake -S . -B build-no-cam -G "Visual Studio 17 2022" -A x64 -DFREZA_ENABLE_CAM=OFF
cmake --build build-no-cam --config Release --parallel 4
ctest --test-dir build-no-cam -C Release --output-on-failure
./build-no-cam/Release/FrezaEgm.exe
```

CAM по умолчанию OFF. Кнопка STL объясняет отсутствие CAM, старые режимы доступны.
ON без установленной зависимости завершается понятной диагностикой при configure;
сборка не притворяется CAM-сборкой. `.github/workflows/windows-cam.yml` добавляет
матрицу ON/OFF, прежний selftest с UDP-loopback и новые проверки. Workflow в этой
сессии не запускался, результаты Windows CI не заявляются.

## Контрольные артефакты

В `VisualStudio/FrezaEgm/data/cam/`:

- `Primer1.STL`: найденная исходная binary-модель, 684 байта, 12 треугольников,
  габариты 20×20×0.5; скопирована без изменений.
- `Primer1-ascii.stl`: те же нормали/вершины в ASCII.
- `Primer1-part.csv`: рассчитанный OCL контур в системе детали:
  `(0,0,0.5) → (20,0,0.5) → (20,20,0.5) → (0,20,0.5) → (0,0,0.5)`.
- `Primer1-base.csv`: тот же результат с демонстрационным переносом:
  `(750,0,600) → (770,0,600) → (770,20,600) → (750,20,600) → (750,0,600)`.
- `sensor-0..3.bin`: фиксированные эталоны protobuf по исходной схеме/сериализатору.
  Точки `(0,0,0)`, `(10,0,0)`, `(750,0,600)`, `(-1.25,0,3.5)`;
  первая seq/tm=0/0, остальные 42/1000. Присутствие нулей и ориентации проверяется
  также декодированием. Фикстуры сформированы независимо как wire-format и сверены
  исполняемыми вызовами неизменённой исходной функции.

При Ø4 и CAM-шаге 0.5: **168 контактов OCL → 5 точек**, длина 80 мм.
Прежняя интерполяция с шагом 2, скоростью 50: **41 точка**, 5 признаков вершин,
первая выдержка 200 мс, последующие 40 мс. Это расчёт таблицы, не измерение
действительного периода сети или движения.
