# Milling Geometry Analyzer: STEP, Безье, траектория и ориентация

Отдельное приложение C++17 для проверки нового способа построения поз.
Исходная ветка — `feature/bezier-offline`, работа продолжается в
`feature/bezier-viewer`. FrezaEgm, его GUI, протокол и RobotStudio не меняются.
Приложение не содержит UDP/EGM-клиента и не управляет роботом.

## Что можно проверить

- Загрузить STEP через OCCT 7.9.3: единицы, B-rep, реальные грани с отверстиями.
- Загрузить прежний `.bpatch` с 16 контрольными высотами, включая mm/inch.
- Открыть встроенную настоящую бикубическую поверхность Безье (`--demo`)
  или вогнутую поверхность (`--bowl`) для проверки врезания плоского торца.
- Вращать/масштабировать 3D-модель, выбирать грань щелчком или списком.
- Видеть растровые проходы, нормали, контрольную сетку Безье, цилиндр фрезы
  и его оси. Проигрывать всю грань одной последовательностью или выбирать отдельный проход.
- Читать текущие XYZ, нормаль, q=(w,x,y,z) и время внутри прохода.
- Выгружать JSON сцены и CSV поз выбранной грани. Это **не CSV FrezaEgm**.

Интерфейс — HTML/Canvas с вращаемой 3D-проекцией; CAD и позы рассчитываются
на C++. При запуске без аргументов приложение открывает локальный интерфейс:
кнопка выбора STEP/STP/.bpatch → модель → выбор грани → параметры → «Рассчитать».
Можно менять диаметр, длину, шаги, допуски, подачу и знак нормали, затем пересчитывать.
При загрузке сначала строится только модель; сотни граней не рассчитываются автоматически.
Ошибка импорта сохраняет предыдущую модель. Расчёт блокирует повторную загрузку.

Интерфейс обслуживается только на 127.0.0.1, на свободном TCP-порту, со случайным
адресом сессии. Это локальный интерфейс анализатора, не EGM-сервер. Нет CDN
или отправки CAD на внешний сервис. Окно консоли оставьте открытым; Ctrl+C
завершает процесс. Python/Node для работы EXE не нужны. CLI дополнительно создаёт
автономные preview.html/scene.json, которые открываются без запущенного сервиса.

## Windows x64 / MSVC 2022

Нужны Git, CMake >=3.21 (для упаковки DLL), Visual Studio 2022 Desktop C++, Windows SDK.
PowerShell из корня репозитория. Сохраните свои локальные изменения перед switch.

```powershell
git status --short
git fetch origin
git switch feature/bezier-viewer
git pull --ff-only origin feature/bezier-viewer

# Первый раз собираются закреплённые OCCT и Eigen; это длительная операция.
cmake -P MillingAnalyzer/cmake/Dependencies.cmake
$deps = Join-Path $pwd 'build-bezier-viewer-deps'
cmake -S MillingAnalyzer -B build-bezier-viewer -G "Visual Studio 17 2022" -A x64 "-DCMAKE_PREFIX_PATH=$deps/occt" "-DEIGEN_INCLUDE_DIR=$deps/eigen"
cmake --build build-bezier-viewer --config Release --parallel 4
ctest --test-dir build-bezier-viewer -C Release --output-on-failure

# Контрольная кривая Безье и автоматическое открытие результата:
.\build-bezier-viewer\Release\MillingAnalyzer.exe --demo --output preview-bezier --open

# Собственная STEP-модель (путь с пробелами заключить в кавычки):
.\build-bezier-viewer\Release\MillingAnalyzer.exe "C:\Models\part.step" --output preview-part --open

# Собственный патч из существующего проекта:
.\build-bezier-viewer\Release\MillingAnalyzer.exe .\VisualStudio\FrezaEgm\data\bezier\crown.bpatch --output preview-patch --open

# Один выбранный face ID из списка просмотрщика, другой инструмент:
.\build-bezier-viewer\Release\MillingAnalyzer.exe "C:\Models\part.step" --face 5 --diameter 4 --length 20 --spacing 1 --step 0.5 --chord 0.01 --angle 3 --output preview-face5 --open
```

Каждая команда должна завершиться успешно до следующей. Выходной каталог
должен быть новым; существующие файлы не перезаписываются. В нём будут
`preview.html` и `scene.json`. Сохраните каталог, чтобы повторно открыть результат.
Параметры задаются в мм, градусах и мм/с; `--help` перечисляет их.

Основной запуск, с загрузкой файлов прямо в программе:

```powershell
.\build-bezier-viewer\Release\MillingAnalyzer.exe
```

В открывшемся окне нажмите «Загрузить STEP или bpatch», выберите файл из любой
папки (например C:\Models), выберите нужную грань и нажмите «Рассчитать выбранную грань».
Затем выберите проход и нажмите «Играть». JSON/CSV сохраняются кнопками экспорта.
Модель остаётся в системе детали; реальное движение не запускается.

Для сборок из GitHub Actions скачайте `MillingAnalyzer-Windows-x64`, распакуйте
полностью, сохраните DLL рядом с EXE. Готовая демонстрация лежит в `demo/preview.html`.

Исходный STL/OpenCAMLib-путь и сборки FrezaEgm ON/OFF — по
[прежней инструкции](14-operator-windows.md); этот анализатор от OpenCAMLib не зависит.

## Геометрия и растровые проходы

STEP читается `STEPControl_Reader`, единицы явно переводятся в мм до переноса
корней. Геометрия грани оценивается `BRepAdaptor_Surface::D1`, учитываются Location
и `TopAbs_REVERSED`. Нормаль — нормализованное `Su × Sv` с поправкой ориентации.
Для `.bpatch` создаётся `Geom_BezierSurface` с заданными контрольными точками:

`S(u,v)=ΣᵢΣⱼ Bᵢ³(u) Bⱼ³(v) Pᵢⱼ`.

Кривая демо: `z=8u(1−u)+4v(1−v)`, XY 20×20 мм. Все единичные веса, 16 полюсов.
В JSON присутствуют контрольные точки и веса для Bezier-граней. STEP-плоскости
и NURBS не подменяются приблизительным bounding box или искусственным fit Безье.

На каждой строке UV выполняется пересечение изопараметрической линии с настоящими
p-curves рёбер (`Geom2dAPI_InterCurveCurve`). Между пересечениями проверяется
принадлежность грани (`BRepClass_FaceClassifier`). Отверстие разделяет строку на
**раздельные рабочие проходы**; режущее перемещение через отверстие не добавляется.
Соседние строки связываются по поверхности. Через отверстия и при недопустимом
отступе связующего участка выполняется отвод и переход над всей моделью.
Порядок строк — zigzag. Строки, совпадающие с trim boundary, пропускаются.

Шаг между строками оценивается в миллиметрах по пяти сечениям поверхности;
это не гарантированная постоянная ширина обработки/высота гребешка.
Вдоль прохода адаптация проверяет 3D-шаг, нормаль и угол ориентации, а отклонение
от хорды — в 1/4, 1/2 и 3/4 интервала. Есть бюджеты глубины/точек.
Это численная проверка, не строгая глобальная оценка ошибки для произвольной NURBS.
Сингулярные производные и неудачный trim вызывают отказ для этой грани.
На моделях с >32 гранями по умолчанию строится только сетка; для расчёта укажите
`--face ID`, чтобы не запускать сотни проходов по сборке шпинделя.

## Ориентация и контакт

Tool +Z — от центра торца к хвостовику идеализированного цилиндра.
`Zt = sign*n`; знак задаётся `--normal-sign 1` или `-1` до расчёта.
Начальная Xt — проекция касательной на плоскость, перпендикулярную Zt;
Yt=Zt×Xt. Далее используется минимальное вращение между последовательными
нормалями: `q_next = FromTwoVectors(Z_prev, Z_next) * q_prev`.
Это дискретный parallel transport: разворот подачи на следующей строке **не**
поворачивает инструмент вокруг собственной оси. На плоскости quaternion постоянен
для всей змейки. На кривой поверхности инструмент наклоняется вслед за нормалью;
постоянный Euler yaw в базе не требуется и не эквивалентен отсутствию осевого spin.
Антипараллельные нормали отклоняются как неоднозначные, q нормализуется.
Формула Xt по подаче в исходном handoff используется только для начальной позы:
это явное уточнение согласно требованию пользователя от 23.11.2026 о запрете
лишнего осевого вращения. [API Eigen 3.4](https://libeigen.gitlab.io/eigen/docs-3.4/classEigen_1_1QuaternionBase.html).
Проверяются `RᵀR=I`, `det(R)=+1`, совпадение Z с нормалью и отсутствие осевой
составляющей каждого приращения quaternion, включая развороты и переходы.

q — активное вращение из системы инструмента в систему детали, порядок **w,x,y,z**.
В пределах прохода выбирается одинаковая полусфера соседних кватернионов.
Анимация использует линейную интерполяцию XYZ и кратчайший SLERP, а не углы Эйлера.
Полная траектория содержит подвод, все рабочие проходы, отводы и переходы.
В селекторе по умолчанию выбрана «Вся грань». Время единое, строго возрастает;
на переходах учитываются и линейная скорость, и предел вращения 30°/с.
Ускорения и суставные ограничения робота ещё не рассчитываются.

Поза центра торца совпадает с точкой контакта поверхности. Это **кандидат**,
а не гарантированно допустимая cutter-location pose. На вогнутой поверхности
нормальный цилиндрический инструмент может врезаться соседней частью торца.
В таком случае результат помечается красным; автоматического выталкивания,
наклона или «исправления» контактной геометрии нет.

Базовая проверка: треугольники всей модели преобразуются в систему фрезы,
обрезаются высотным интервалом цилиндра, проверяется пересечение их проекции
с диском торца. Проверяются исходные и промежуточные позы XYZ+SLERP, шаг не
более min(0.5 мм, D/4), угол не более 2°. Погрешность сетки 0.02 мм,
контактный зазор теста 0.001 мм. Проверка выборочная: возможны пропуски между
позами и из-за аппроксимации. Центр цилиндра дополнительно классифицируется относительно solid для выявления полного вложения.
Статус «не найдено» означает только отсутствие находок этим тестом.
Держатель, кабели, заготовка, оснастка и робот в тест не входят.

## Граница внедрения

Это проверяемая CAD/pose-визуализация, а не законченный процесс фрезерования.
Следующие модули handoff остаются отдельной работой:

- регистрация шпиндельной сборки и реального TCP, полный collision checking;
- переходы между разными гранями и строгая проверка непрерывных swept volumes;
- stock, припуск, послойная черновая обработка и остаточный материал;
- IK, суставные ограничения, сингулярности, скорости и ускорения;
- отдельное согласованное расширение EGM на ориентацию и испытания RobotStudio;
- ограниченная силовая коррекция и watchdog.

Старый TCP не меняется. Никакой длины инструмента к XYZ автоматически не прибавляется.
Позы остаются в системе детали. Этот CSV нельзя подавать в прежний XYZ-парсер ABB.

## Связанная последовательность для всей выбранной грани

1. Центры фрезы отступают от всех настоящих trim-рёбер минимум на D/2+0.02 мм.
   Расстояние вычисляется OCCT, переход допустимо/недопустимо уточняется делением.
   Строки также отступают от края; шаг между ними не может превышать диаметр.
   Это консервативный дискретный отступ, а не доказательство полного съёма материала:
   у границ остаётся технологический зазор, stock/scallop-модель отсутствует.
2. Подвод/отвод выполняются вдоль локальной +Z инструмента. Для текущего связующего
   алгоритма ось должна иметь Z>0.2 в системе детали; боковые и нижние поверхности
   требуют другого размещения/стратегии и получают явный отказ соединения.
3. Для близких концов соседних строк сначала строится кривая на CAD-поверхности:
   линейный путь в UV вычисляется через OCCT D1 и адаптивно дробится по 3D-шагу,
   углу нормалей и допуску хорды min(chord, 0.005 мм). Проверяется принадлежность
   грани в четвертях интервала; расстояние **всей выходной хорды** до каждого
   trim-ребра вычисляется `BRepExtrema_DistShapeShape` и должно быть ≥D/2+0.005 мм.
   Это не замена поверхности прямым отрезком между концами проходов.
   Если соединение не проходит геометрическую проверку, используется отвод.
   Сегменты одной строки по разные стороны отверстия всегда соединяются сверху.
   Переход над моделью проходит на общей высоте: верх всей модели + sqrt(L²+(D/2)²) + clearance.
   Этот запас учитывает цилиндр и промежуточные ориентации. Переходы через отверстия
   выполняются над моделью. В самом проходе точки не перескакивают через trim.
4. Весь путь дискретизируется по XYZ и углу, quaternion меняется через SLERP.
   Для подводов, отводов и переходов выполняется та же проверка цилиндра по всей сетке.
   Если найдены коллизии, путь остаётся видимым как диагностический кандидат, с красными
   участками; виртуальный EGM-адаптер такой CSV отклоняет.
5. JSON содержит faces[].trajectory; poses[].motion означает сегмент, заканчивающийся
   в этой позе: 0 обработка, 1 отвод, 2 переход, 3 подвод. CSV режима «Вся грань» имеет
   pass_id=0 и общую шкалу time_s. CLI сохраняет face-N.poses.csv рядом с preview.html.

На встроенной выпуклой Безье при настройках по умолчанию: 10 рабочих проходов,
677 поз полной последовательности, 25.610 с; один подвод и один отвод,
между строками — движение по поверхности без холостых переходов. Это время математического просмотра,
не прогноз цикла ABB. Изменение параметров меняет эти значения.

Отдельный эксперимент с двумя задачами RAPID и единственным отправителем поз:
[RobotStudio pose + force](../experiments/robotstudio_pose_force/README.md).


## Математическое ядро и соответствие handoff

Обязательный набор установлен и собирается скриптом:

```powershell
cmake -P MillingAnalyzer/cmake/Dependencies.cmake
```

- C++17: локально Apple Clang, в Windows CI MSVC 2022 x64 (существующая инфраструктура).
- CMake: требуется 3.21 или новее для упаковки Windows DLL.
- OCCT 7.9.3: STEP, B-rep, trim, производные поверхности, расстояния и mesh.
- Eigen 3.4.0: векторы, матрицы, минимальные вращения, quaternion и SLERP.
- cpp-httplib 0.18.3: локальный интерфейс. Визуализация использует Canvas.
- Python 3: только запуск HTTP/UDP-тестов, приложению не нужен.

Версии и Git revision закреплены в `cmake/Dependencies.cmake`; системные пути
другого компьютера не нужны. OpenCAMLib остаётся отдельной зависимостью прежнего
STL-режима. FCL, CGAL, OMPL не требуются этому этапу и не подключены: handoff явно
предписывает начать с OCCT + Eigen, а не устанавливать все дополнительные пакеты.
Установка библиотеки сама по себе не реализует stock removal или IK.

Реализован этап raster finishing одной грани. Черновые Z-слои и модель остатка,
регистрация CAD-шпинделя к измеренному TCP, коллизии держателя/робота, IK и реальный
силовой датчик остаются следующими этапами handoff. Текущую змейку нельзя считать
расчётом удаления объёма заготовки. Существующий EGM и tooldata не изменены.
